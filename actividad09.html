Actividad 09

"Path Traversal: Bypass con Secuencias Anidadas"

↓ Descargar Reporte (PDF)

Descripción General

Explotación exitosa de Path Traversal evadiendo un filtro de sanitización deficiente. Se inyectaron secuencias anidadas (....//) para obligar al servidor a reconstruir el patrón de salto de directorio tras su limpieza superficial, logrando extraer el archivo /etc/passwd.

Objetivos de la Práctica

  • Identificar la presencia de filtros de seguridad no recursivos que eliminan secuencias de salto de directorio.
  • Comprender la lógica de procesamiento del servidor para manipular la sanitización a favor del atacante.
  • Aplicar técnicas de ofuscación y secuencias anidadas para reconstruir la carga útil (payload) original y acceder a archivos restringidos.

Desarrollo

El ataque se ejecutó explotando la forma en que la aplicación intentaba protegerse a sí misma:

  1. Intercepción inicial: Se interceptó la petición que solicitaba un archivo interno, por ejemplo, mediante el parámetro filename.
  2. Prueba del filtro: Al inyectar el payload estándar ../../../etc/passwd, el servidor procesó la petición pero eliminó las secuencias ../, dejando la ruta inservible y devolviendo un error o el archivo incorrecto. Esto indicó que la sanitización no era recursiva (es decir, solo eliminaba el patrón una vez).
  3. Inyección de Secuencias Anidadas: Se construyó un nuevo payload utilizando el patrón ....//. Al enviarlo, la función de limpieza del servidor detectó el ../ interno y lo eliminó.
  4. Reconstrucción del Payload: Tras la eliminación de los caracteres internos, los puntos y barras restantes (.. y /) se juntaron automáticamente, formando un nuevo ../ válido directamente en la memoria del servidor.
  5. Explotación: La petición final enviada fue filename=....//....//....//etc/passwd. El servidor la procesó, evadió el filtro y devolvió exitosamente el archivo crítico de configuración.

Conclusiones

Este laboratorio demuestra una de las fallas de lógica más comunes en el desarrollo web: implementar defensas superficiales que no procesan la entrada de manera exhaustiva. Una sanitización que solo elimina "palabras malas" una sola vez es trivial de evadir usando técnicas de ofuscación anidada.

Para defenderse correctamente, la aplicación no debería depender de limpiar las entradas maliciosas (stripping), sino validar que la entrada final cumpla con estrictos criterios permitidos (whitelisting) o utilizar funciones de seguridad nativas del framework que normalicen y validen la ruta antes de interactuar con el sistema de archivos.
